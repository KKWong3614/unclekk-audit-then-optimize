# 诊断清单法 — Diagnostic Checklist

## 核心原则

Skill 质量审计的首要信号应该是**缺陷是否存在**（grep 可判定），而非"打分 1–10"。缺陷清单零主观方差；一个 1–10 的主观维度可能出现 9.5–11 的方差，足以吃掉 2–3 个确定性加分维度。

## 使用方法

每次对 skill 做质量评估时，**先跑诊断清单**（输出 P0/P1/P2 缺陷列表），再用数值 rubric 做辅助排序。数值 rubric 只在缺陷数持平或需要版本间排序时使用，不作为独立决策依据。

## 缺陷清单（持续追加）

按严重程度分组。每一行应能对应一个确定的 grep / pattern / 运行时检测方式。

### P0 缺陷（阻断/安全）
- [ ] 脚本含硬编码本地路径（`require('/Users/...')`、`/home/`、绝对 `C:\`）
- [ ] 无输入校验的公共入口（mcp tool / CLI entrypoint 无参数检查）
- [ ] 凭据或敏感数据写入日志或明文配置
- [ ] 依赖声明与实际 import 不一致（e.g. `fastmcp` vs `mcp`）
- [ ] 跨进程写同一 roadmap.json 无锁 / 无原子写（unclekk-roadmap-planner 类工具）

### P1 缺陷（误导用户/断裂流程）
- [ ] 文档声称有 X 个工具，实际代码只有 Y 个（phantom tools）
- [ ] 版本号五处（SKILL.md frontmatter / package.json / _meta.json / README / CHANGELOG 标题）不一致
- [ ] 路径检测函数未做运行时验证——只读代码，未实际调用
- [ ] bash 脚本修改后未跑 `bash -n`
- [ ] import 清理时未检查函数签名的 type hints（List / Dict / Optional 等）

### P2 缺陷（可执行性 / 可用性）
- [ ] 软化措辞 ≥3 处（"建议"、"可以考虑"、"根据情况"、"灵活把握"、"视情况而定"）
- [ ] 失败模式未编码（缺少"如果 X 失败 → Y"的显式分支表）
- [ ] 决策分叉清单缺失或只是括号关键词堆，无可逐条扫描的检查项
- [ ] frontmatter 与正文存在**真实**重复声明（同一内容两处完整写出，非重定向指针）
- [ ] 存在重定向指针被误判为重复声明的风险——区分 pointer（"见文件头注释"）与 declaration（完整再写一遍）
- [ ] 测试 prompt 缺失或全部为 dry_run（dim8 实评为 0）
- [ ] 多平台路径候选列表缺失目标平台的候选（Windows 缺 `AppData\Local\hermes\`）
- [ ] 配置文件多副本（sync-config 类）未同步——只改了非权威副本

## 诊断清单优先 vs 数值 rubric

| 场景 | 首选工具 | 理由 |
|------|---------|------|
| 版本间决策（v1.1 vs v1.3 是否采纳） | 诊断清单 delta | 新增/消除的缺陷是确定性信号 |
| 整体质量排序 | 诊断清单 → rubric 辅助 | 高缺陷数优先，不计主观分数 |
| 单个维度的可信度检查 | 多 judge 方差分析 | 同一维度 Δ ≥ 1.5 → 该维度标记低信度，不纳入总分 |
| 增量改进验收 | 清单项 checked/unchecked 变化 | 比总分 ±2 分更可靠 |

## 与数值 rubric 的关系（不是替代）

诊断清单是**默认通过**，9 维 rubric 是**辅助排序工具**。两者关系：
- 缺陷清单回答"有没有问题" → 决策依据
- 数值 rubric 回答"在同样无缺陷的候选里哪个写得更清晰" → 排序依据
- 永远不要让一个高方差的数值维度（dim7 方差 9.5–11 是已知事实）否决一个零方差的缺陷清单信号

## 来源

来自 grill-me v1.1→v1.3 评估教训（2026-07-25）：dim7 架构维度方差 9.5–11 吃掉了 dim3（失败模式表，满分）+ dim5（分叉清单，满分）的确定性增益，导致评分倒挂。独立审计长对 v1.3 唯一扣分项是 dim7 对"重定向指针"的误判（pointer ≠ declaration），被修复后增量版本实际质量优于基线但被回滚——诊断清单 delta（缺陷 -1，无新增缺陷）明确指向"采纳"，而数值总分（-4.5）指向"回滚"，两套工具结论冲突时以清单为准。
