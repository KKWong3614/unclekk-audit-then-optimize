# 独立第三方审计长（Multi-Round Meta-Audit Loop）

当用户要求"用达尔文和 skill-evolution 优化某 skill"时，主 Agent 必须是**任务派发者**而不是优化执行者。
优化由独立子 Agent（"审计长"）完成，主 Agent 不参与、不评分、不预读文件。

## 触发条件

用户说"用达尔文和 skill-evolution 优化某 skill"、"调独立审计长"、"多轮优化直到触顶"时，用此 pattern 而不是主 Agent 自己做。

## 铁律

1. **主 Agent 不读目标 skill 的源文件**（SKILL.md / harness.py / 等）。只传递：
   - 绝对路径 + 文件名列表
   - Darwin 9 维 rubric 定义
   - SkillEvolution 三阶段流程
   - 9 条审计规则
2. **审计长只读文件 + 自己评估 + 自己生成补丁 + 自己跑测试**
3. **主 Agent 收到审计长报告后必须独立验证**（不能只看"测试通过"就信）
4. **主 Agent 不预读审计报告原文**——只读摘要，不接收任何来自主 Agent 的评分

## 与三步法的区别

本模式的"审计长"在**同一 leaf** 内完成评估→生成补丁→跑测试，属于**自审式迭代**。这与 SKILL.md 三步法中"优化器与审计员必须分离"的核心前提不同——三步法的独立复审 C 由**另一个 leaf 或主 Agent 在轮次之后**执行。本模式的 leaf 自审**不等同于独立 C**；真正的独立 C 须由主 Agent 在每轮结束后独立验证承担（铁律第 3 条），或通过派发独立 leaf 进行跨轮复审。

**换言之**：本模式解决的是"优化触顶"问题（达尔文 hill-climbing），三步法解决的是"自评分虚高"问题。两者目标不同，不可混淆。

## Agent 参数模板（审计长派发）

```python
# 本环境用 Agent 工具（subagent_type="general-purpose"）；delegate_task 仅当宿主支持时作别名
Agent(
    description="独立审计长（达尔文+SkillEvolution 优化）",
    subagent_type="general-purpose",
    prompt="""
    目标 skill 路径：C:/Users/user/AppData/Local/hermes/skills/<skill-name>/
    包含文件：SKILL.md, scripts/harness.py, scripts/test_harness.py, ...
    Darwin 9 维 rubric 定义（每个维度 1-10 分，含权重公式）
    SkillEvolution 三阶段闭环（Phase 1-4）
    9 条审计规则
    触顶条件说明（上轮 Δ 值）
    目标：作为独立第三方审计长，用达尔文 + SkillEvolution 优化该 skill，直到触顶
    """,
)
```

## 触顶判定（达尔文 hill-climbing）

| 条件 | 判定 |
|------|------|
| 连续 2 轮真实有效 Δ < 2 | **触顶成立**，停止迭代 |
| 本轮 Δ ≥ 2 且是真 bug/真改进 | 未触顶，继续 |
| 本轮 Δ 中大部分是维度重评带来的分数膨胀 | 剔除膨胀后看"真实有效 Δ" |

**维度重评膨胀的识别方法**：
- 同一个 artifact 的不同评分者可能给不同基线（因为对同一维度的"完整度"判断不同）
- 基线差异 ≠ 真实进步
- 真实 Δ = 优化后分数 - 基线分数 - 维度重评带来的分数膨胀
- 膨胀检测：基线被重新评估时，如果某些维度从 8 跳到 10，大概率是归一差异而非代码真变好了

## 主 Agent 收到审计长报告后的独立验证步骤

1. **测试通过验证**：`python scripts/test_harness.py` → 确认测试数和通过数
2. **CLI 端到端验证**：对 harness 类 skill，跑 INGEST→PLAN→EXEC→REVIEW→AUDIT→SETTLE 全流程
3. **关键 bug 修复验证**：独立构造测试用例验证审计长声称修复的 bug（如沙箱属性链逃逸，用 `outputs.__class__` 测试）
4. **results.tsv 一致性**：审计长写的条目时间戳/分数/维度增量是否与验证结果一致
5. **不依赖审计长的分数**：分数归一化方式不可比（不同审计长用不同归一口径），只看测试结果和 bug 修复

## 多轮迭代工作流

```
主 Agent
  → Agent(审计长第 1 轮)
    → 审计长：Phase 1-4 完整执行（策略变体生成 → 比较选择 → 独立审计 → 应用补丁）
    → 返回：基线+优化后分数、策略对比、审计通过率、results.tsv 条目
  → 主 Agent：独立验证审计长声称的 bug 修复和测试通过
  → 判断是否触顶（连续 2 轮真实有效 Δ < 2？）
  → 如未触顶：
    → Agent(审计长第 2 轮)
    → ...（重复直到触顶）
```

## 已验证案例（unclekk-harness, 2026-07-27）

|------|--------|--------|---------|
| 第 1 轮 | leaf | +3.72 | 沙箱属性链逃逸 + 死引用 |
| 第 2 轮 | leaf | +1.3 | workspace abspath + 可写性验证 |
| 第 3 轮 | leaf | +0.63 | stage-gate + 空输出阻断 |
| **触顶** | ✅ 连续 2 轮 Δ<2 | — | — |

测试增量：17 → 33 项（+16 项新测试）
三轮 9 条规则审计通过率：全部 9/9 PASS

## 经验教训

- **不要伪造"并行 subagent"**：如果 Agent 不在工具集中，改成由审计长独立生成并逐项执行，诚实标注
- **分数不能直接加减**：不同审计长的归一方式不同（主 Agent 用 74-92 区间，审计长用 40-50 区间），横向比较无意义
- **真实收益比分数重要**：3 轮独立审计发现了 2 个真 bug（沙箱逃逸 + 死引用），比任何分数提升都更有价值
- **审计长不会改 SOUL.md 和其他 skill 的文件**：这是铁律，但主 Agent 要确认
- **测试增量是重要信号**：即使分数看起来"没涨多少"，测试覆盖面的扩大本身就是价值
