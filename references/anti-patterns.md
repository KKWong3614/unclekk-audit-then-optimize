>
> Common anti-patterns vs corrected examples, drawn from real cases in the unclekk ecosystem.

## 反模式 1：让优化器兼任审计员（自审自）

**❌ 错误用法**
```python
# 优化器刚改完文件，同一个上下文给自己打分
score = optimizer.evaluate_own_work(target_skill)   # 必然乐观
```

**✅ 改进示例**
```python
# 优化器与审计员必须分离：fresh 子代理独立审计
Agent(
  description="独立审计 <SKILL_NAME>",
  subagent_type="general-purpose",      # 全新上下文
  prompt="你是独立第三方审计员（fresh 上下文，只评不改）…",
)
```

**为什么是反模式**：刚编辑完文件的优化器知道自己修了什么、假设自己修对了、对产出乐观。自评分 86 vs 独立审计 82（darwin-evolver 案例），虚高是常态。

**禁忌**：绝不让同一个人 / 同一上下文既是优化器又是审计员。

## 反模式 2：审计员工具名写死为不存在的工具

**❌ 错误用法** <!-- audit-guard:ignore -->
```python
delegate_task(role="leaf", toolsets=["file", "terminal"])   # 本环境不存在的工具
```

**✅ 改进示例**
```python
# 用宿主真实存在的 Agent / Task 工具派发 fresh 子代理
Agent(subagent_type="general-purpose")   # delegate_task 仅当宿主支持时作别名
```

**为什么是反模式**：跨生态移植（Claude Code → Hermes / WorkBuddy）时，移植代理对工具名不兼容视而不见——"复制即可跑"的模板实际跑不通，这是 P0 级缺陷。

**禁忌**：发布前 grep 全仓禁用工具名（`delegate_task` 等），出现时必须同行含"别名"限定，否则 FAIL（`audit_guard.py selfcheck` 已内置此项）。

## 反模式 3：只修措辞不修算法（文档承诺 ≠ 代码实现）

**❌ 错误用法**
```
文档写「跨量规自动转百分比」，代码却 diff = b - c（原始分作差），--rubric-max 是装饰参数。
→ /90 量规下 B=80 C=77：文档判虚高(3.33%>3%)，代码判"小幅波动"——与文档结论相反。
```

**✅ 改进示例**
```
diff = (b - c) / rubric_max * 100   # 转相对百分比，阈值 3（百分点）
→ /90 量规 B=80 C=77：+3.33 百分点 > +3 → 判「自评分虚高，以 C 为准」✓
```

**为什么是反模式**：技能定义的规则必须与其附带的示例/算法一致。规则写在文档而代码没实现，是最隐蔽的 P0-3 残留——"技能自身示例中出现的反例是 P1 缺陷，不是『需要进一步说明』"。

**禁忌**：改文档措辞前先确认算法真的实现；用变异测试/反例实测验证。

## 反模式 4：验证只跑"能运行"，不验证"能检出"

**❌ 错误用法**
```
"硬代码是否真硬：复跑 selfcheck / preflight / loop / closure 全部通过（退出码 0）"
→ 退出码 0 只证明脚本能运行，不证明它能检出缺陷。
```

**✅ 改进示例**
```
python scripts/audit_guard.py selftest
→ 5 组变异（断链 / LICENSE CRLF / @ 幽灵路径 / 互引孤儿 / 纯孤儿）全部被检出
→ 才算"能检出"，覆盖面成立。
```

**为什么是反模式**：本技能核心警告「声称已核验而实际未核验」在自身复现过 3 次（CRLF 复发、C 轮虚假 grep 断言、selftest 假自证）。根因一致：验证方法只验"能运行"不验"能检出"。

**禁忌**：声称"已核验"必须附可复现的证据（命令输出 / 变异测试结果），禁止凭印象断言。

## 反模式 5：示例/计数漂移不核对（正文 vs references 不一致）

**❌ 错误用法**
```
正文写「版本号四处」，references/diagnostic-checklist.md 也写「四处」，但代码已扩为五处校验。
→ 计数漂移，规则形同虚设。
```

**✅ 改进示例**
```
以 references/ 与代码实现为事实来源，统一为「版本号五处（…含 CHANGELOG 标题）」。
→ 发布前跑 selfcheck 跨文件计数检查，冲突即 WARN/FAIL。
```

**为什么是反模式**：跨文件计数（"N 类失败模式"、"版本号 N 处"）在正文、references、CHANGELOG、代码间经常漂移——正文是摘要，事实来源才是真相。

**禁忌**：凡是重复计数的数字，发布前必须 grep 全仓核对一致。

## 反模式 6：无上限的闭环递归

**❌ 错误用法**
```
修复 → 复审 → 又发现问题 → 再修复 → 再复审 → …… 无限循环（无界递归）。
```

**✅ 改进示例**
```
python scripts/audit_guard.py loop --round N --max 3   # 硬上限 MAX_ROUNDS=3
→ 达到上限强制 STOP，未闭合项交主代理人工收口。
```

**为什么是反模式**：闭环方法论自己也会递归成无底洞。MAX_ROUNDS=3 是硬上限（脚本状态自增，忘记递增也会被脚本纠正）。

**禁忌**：不要用"再跑一轮审计"拖延收口；达到上限就人工收口。

## 禁忌用法清单（快速自检）

| # | 禁忌 | 后果 | 替代 |
|---|------|------|------|
| 1 | 优化器兼审计员 / 同一上下文自评 | 自评分虚高，闭环失去意义 | fresh 子代理独立审计 |
| 2 | 写死不存在的工具名（delegate_task） | 模板跑不通，P0 级 | 用宿主真实工具，仅作别名 |
| 3 | 文档承诺算法未实现（修措辞不修算法） | 规则与行为矛盾，最隐蔽的 P0-3 | 变异测试/反例实测 |
| 4 | 声称"已核验"但不附可复现证据 | 虚假断言，可信度崩塌 | 附命令输出/变异结果 |
| 5 | 计数/版本/链接漂移不核对 | 规则形同虚设 | 发布前 selfcheck + grep 全仓 |
| 6 | 闭环无限递归 | 资源浪费、收不了口 | MAX_ROUNDS=3 硬上限 |
| 7 | 审计员带写入/发布工具 | 违反"只评不改"，可能改坏目标 | toolsets=['file','terminal'] 只读 |
| 8 | 不给绝对路径 / 审计上下文包残缺 | 叶节点代理无目录感知，审计失真 | 绝对路径 + 文件清单 + 先前发现 |
